## Correctif 1 — gel lors de la saisie avec un provider UIA lent

Référence publique : NVDA issue #20654.

### Défaut

`speech.speakTypedCharacters()` appelait `api.isTypingProtected()` avant même de vérifier si l'écho caractères/mots était actif ou si le caractère pouvait être prononcé. La résolution de l'état protégé peut déclencher des appels d'accessibilité inter-processus et bloquer le thread principal lorsqu'un provider UIA est lent.

### Changement

Fichier : `source/speech/speech.py`

- lecture des modes d'écho avant toute requête de protection ;
- résolution paresseuse de `api.isTypingProtected()` uniquement sur un chemin qui doit réellement parler ou mémoriser du texte ;
- aucun appel de protection lorsque les deux échos sont désactivés ;
- aucun appel de protection pour un caractère de contrôle inutile avec tampon vide ;
- masquage `*` conservé pour les champs protégés ;
- tampon de mots effacé lorsque l'écho des mots est désactivé afin de ne pas conserver de texte clair inutilement ;
- logique de suppression de caractères conservée.

### Couverture ajoutée

`tests/unit/test_speech.py` couvre notamment :

- échos désactivés => aucune requête de protection ;
- caractère de contrôle => aucune requête inutile ;
- caractère protégé => `*` prononcé ;
- mot protégé => jamais prononcé en clair ;
- compteur de suppression conservé.

Un harness autonome est fourni dans `tests/zeroRegression_speakTypedCharacters.pyqa`.

Résultat local : `PASS`.

## Correctif 2 — annonces erronées de caractères braille Unicode

Référence publique : NVDA issue #20632.

### Défaut

Certaines entrées de dictionnaires annonçaient les points 1-2-3 à la place des points 4-5-6 pour des caractères braille Unicode. Le défaut n'était pas limité au dictionnaire anglais.

### Changement

- 57 lignes corrigées dans 19 locales : `bs`, `da`, `de`, `en`, `es`, `fi`, `gl`, `hr`, `it`, `ko`, `pl`, `pt_BR`, `ro`, `sk`, `sr`, `ta`, `tr`, `uk`, `vi`.
- motifs principaux corrigés :
  - `⡸` => points 4 5 6 7 ;
  - `⢸` => points 4 5 6 8 ;
  - `⣸` => points 4 5 6 7 8 ;
- erreur supplémentaire roumaine :
  - `⠸` => points 4 5 6.

Les formulations localisées ont été préservées ; seuls les numéros de points explicitement énumérés et mathématiquement faux ont été remplacés.

### Couverture ajoutée

`tests/unit/test_characterProcessing.py` vérifie désormais les 255 motifs braille anglais non vides à partir du codage binaire Unicode U+2801–U+28FF.

Le harness `tests/zeroRegression_brailleSymbols.pyqa` effectue également :

- contrôle exhaustif des 255 motifs anglais ;
- contrôle des entrées ciblées explicitement numérotées dans les dictionnaires localisés.

Résultat local :

`PASS: Unicode braille symbol audit (English=255, localized explicit targets=88)`

## Correctif 3 — cache de modules d’extensions après mise à jour

Référence amont : commit NVDA `fa298b9199b41badb5e58bd5979bfcbcf34e477d` / PR #20715, correctif de #18971.

### Défaut

Depuis 2026.1, `Addon._cleanupAddonImports()` comparait `module.__name__` avec le chemin disque de l’extension. Cette comparaison ne peut pas identifier les modules importés indirectement depuis le répertoire de l’extension. Après une mise à jour, du code de l’ancienne version pouvait donc rester dans `sys.modules` jusqu’au redémarrage suivant.

### Changement

Fichier : `source/addonHandler/__init__.py`

- comparaison basée sur `module.__file__` ;
- modules sans `__file__` ou avec `__file__ = None` conservés ;
- normalisation de casse via `os.path.normcase` ;
- séparateur final imposé sur le préfixe afin qu’un dossier voisin tel que `myAddonExtra` ne corresponde pas à `myAddon`.

Le test unitaire amont `tests/unit/test_addonHandler/test_addonImports.py` est repris. Un harness autonome supplémentaire, `tests/zeroRegression_addonCleanup.pyqa`, exécute la méthode réelle extraite du source sans charger les dépendances Windows de NVDA.

Résultat local : `PASS`.

## Correctif 4 — runtime VC++ du host de synthétiseurs 32 bits

Référence amont : commit NVDA `83cbc5e09bac6973fab563ddb14618f315857fae` / PR #20706, correctif de #20088.

### Défaut

`nvda_synthDriverHost.exe` 32 bits dépend de `vcruntime140.dll`, mais le runtime n’était pas inclus dans son paquet. Sur un système sans redistribuable Visual C++ x86 installé globalement, le host pouvait échouer dès le chargement et empêcher l’utilisation de synthétiseurs SAPI 32 bits.

### Changement

Fichier : `runtime-builders/synthDriverHost32/setup-runtime.py`

- recherche déterministe de `vcruntime140.dll` dans le runtime Python de build ;
- erreur explicite si le DLL est introuvable ;
- ajout du DLL aux `data_files` du host 32 bits.

Le harness autonome `tests/zeroRegression_synthDriverHost32Runtime.pyqa` vérifie la résolution du runtime, l’échec explicite en absence du DLL et sa présence dans la déclaration de packaging.

Résultat local : `PASS`.

## Problèmes étudiés mais volontairement non patchés

L'objectif n'est pas de convertir une hypothèse en correctif. Les cas suivants restent hors du paquet tant qu'une solution robuste n'est pas établie :

- LibreOffice Writer / braille stale (#20625) : l'analyse amont indique que le premier PR spécifique Writer ne traite probablement pas la bonne cause racine ; le comportement de `TreeCompoundTextInfo._findContentDescendant` reste à résoudre proprement.
- Windows Start refined search (#20530) : reproduit également avec Narrator et attribué à Microsoft dans le ticket.
- Magnifier / filtrage couleur maintenu (#20750) : le besoin de distinguer une pression réelle de l'auto-repeat est encore en conception ; pas de throttling arbitraire ajouté.
- Magnifier / caret Firefox (#20415) : reproduction confirmée mais investigation encore ouverte autour de l'obtention intermittente de la position caret.
- Screen Curtain / redémarrage Magnifier (#20518) : ticket ouvert sans correctif amont établi.
- Menus Win32 32 bits / DPI > 100 % sous NVDA 64 bits (#19225 / #20158, PR #20698) : le correctif amont est conséquent et dépend d’appels Win32/DPI et de tests manuels multi-applications ; il n’est pas backporté sans validation Windows dédiée.

## Ce qui ne peut pas être déclaré validé dans cet environnement

Le conteneur courant n'est pas Windows et ne possède pas les dépendances NVDA Windows (`comtypes`, toolchain Visual Studio, etc.). L'exécution directe de la suite unitaire officielle s'arrête donc avant les tests sur l'import Windows, et Ruff ne peut pas être téléchargé ici car l'accès PyPI du conteneur est indisponible.

Il serait incorrect de déclarer ces barrières comme passées.

Le fichier `NVDA-HARDENED-VALIDATE.ps1` est inclus dans la source. Sur Windows, il exécute sans auto-corriger le code :

1. synchronisation des groupes de dépendances verrouillés ;
2. quatre harness de non-régression ;
3. `ruff check` ;
4. `ruff format --check` ;
5. `scons source` pour générer les interfaces/dépendances de source ;
6. `pyright` sur l’arbre préparé ;
7. tests unitaires officiels ;
8. tests système officiels avec le tag explicite `--include NVDA` exigé par NVDA ;
9. contrôle POT ;
10. contrôle des licences ;
11. `scons dist` ;
12. `scons launcher`.

Le script retourne le code `1` si au moins une barrière échoue et produit un journal ainsi qu'un résumé dans `validation-artifacts`. Le packaging est **fail-closed** : si une barrière précédente échoue, `dist` et `launcher` sont marqués `SKIP`. Par défaut, les binaires de test sont versionnés `2026.2-hardened-test` afin de ne pas être confondus avec la release officielle.

## Statut

Tous les correctifs que cet audit permet de démontrer et de tester sans hypothèse ont été appliqués. Le paquet ne prétend pas être une nouvelle release officielle NVDA ni garantir mathématiquement zéro bug. Les problèmes encore ouverts et non résolus en amont restent explicitement identifiés au lieu d'être masqués par des patches spéculatifs.


## Consolidation du ZIP de test

L’export ZIP GitHub de NVDA ne matérialise pas les sous-modules Git. Le paquet final contient donc un manifeste figé de **13 sous-modules** et `NVDA-HARDENED-PREPARE-SOURCE.ps1`, qui récupère chaque dépôt au **SHA exact de `release-2026.2`**, vérifie le commit puis initialise récursivement ses éventuels sous-modules imbriqués. Aucune branche flottante n’est utilisée pour la préparation.

Le lanceur `RUN-NVDA-HARDENED-TESTS.cmd` enchaîne cette préparation puis `NVDA-HARDENED-VALIDATE.ps1`. La validation Windows finale reste volontairement à exécuter sur une machine Windows disposant de Git, Visual Studio et des prérequis NVDA.


## Révision du validateur — 2026-09-03

Après le premier passage Windows, plusieurs sorties natives écrites sur `stderr` étaient transformées par PowerShell en `NativeCommandError` alors que le programme natif n’avait pas encore été jugé par son code de sortie. Le validateur a été corrigé pour journaliser `stdout`/`stderr` en UTF-8 et considérer `$LASTEXITCODE` comme verdict natif.

La séquence a également été corrigée afin d’exécuter `scons source` avant Pyright, ce qui prépare les artefacts générés utilisés par les imports COM/UIA/Louis. Les tests système utilisent désormais `--include NVDA`, conformément au mécanisme de garde officiel de la suite Robot NVDA.

Enfin, la configuration `licensecheck` reprend les exceptions de métadonnées déjà reconnues par le NVDA amont actuel pour `pyphen`, `l2m4m`, `detect-secrets`, `fast-diff-match-patch` et `requests`. Cela ne désactive pas le contrôle de licences : seules ces exceptions nommées sont ajoutées.
